# scaffold-eth: tests

Run from the repo root: `node scripts/verify.mjs scaffold-eth` (add `--full` for the real project build). No API keys, wallets or funds; nothing is sent to any chain.

Scaffold-ETH is a project template, not a library, so the skill's code only means something inside a generated project. Every check therefore starts from a real `create-eth@2.0.23 se-app -s hardhat` (the version the skill pins, installed as a devDependency). create-eth needs `yarn` and a git identity: `yarn@1.22.22` comes from devDependencies (the project then runs its own Yarn 4.13 through `yarnPath`, so no corepack or global install), and git uses a throwaway `GIT_CONFIG_GLOBAL` file written by `lib.mjs`.

| Script | What it checks |
| --- | --- |
| `typecheck` | `tsc` on `live.ts`, then `typecheck.mjs`: scaffolds the template with `--skip-install` (a few seconds) and type-checks the blocks inside copies of its `packages/nextjs`, with the template's own `tsconfig.json`, hooks and utils. The frontend packages come from this folder's `package.json` at the exact versions the template's `yarn.lock` resolves (next 16.2.12, wagmi 2.19.5, viem 2.53.1, rainbowkit 2.2.11, @scaffold-ui/* ...). **Variant A**: generated `scaffold.config.ts` with the chains.md snippet applied, `chains.hardhat` first and the recipe 4b `arcMainnet` last; pages from SKILL.md, quickstart.md, recipe 3 (YourContract read/write/event history) and the recipe 6 wagmi read. **Variant B**: recipe 4a `scaffold.config.ts` with every commented chain uncommented, recipe 4b `customChains.ts`, recipe 6 `externalContracts.ts` (WETH on 4801) and the WETH hook fragment. **Hardhat**: recipe 4c networks typed as hardhat 3.19.0 `HardhatUserConfig["networks"]`; the recipe 2 deploy script is compared statement by statement with the template's generated `deploy/00_deploy_your_contract.ts` (it is fully type-checked in `build`). **Negative checks**, so the above can't pass vacuously: errors.md 5 (WETH hook with hardhat first gives `'"WETH"' is not assignable to type '"YourContract"'`), errors.md 6 (external contract without `deployedOnBlock` breaks the template's `useScaffoldEventHistory.ts` with TS2345) and errors.md 3 (Hardhat 3 network without `type` is rejected). |
| `live` (`live.ts`, viem 2.53.1, the template's version) | Driven by the blocks themselves: each of the six chains in the chains.md snippet answers with the right chain ID and a block, through the snippet's `rpcOverrides` for Arc testnet; the IDs written next to each chain in recipe 4a match viem; viem's default Arc testnet RPC is probed (informational: if it answers again the override is optional); the recipe 4b `defineChain` (imported from the block) answers as chain 5042; every recipe 4c Hardhat URL answers with the chain ID of the viem chain of the same name; recipe 6 WETH predeploy on World Chain Sepolia returns `WETH`/18/totalSupply and `deployedOnBlock` is in the past; a 100-block `eth_getLogs` (recipe 6 `blocksBatchSize`) works (a 500-block range is probed, informational); Sourcify lists all six testnets and Etherscan V2 lists 480/4801/130/1301/5042 (chains.md, recipe 5); the latest create-eth on npm is printed. Unreachable services exit 75 (reported as "network"). |
| `build` (`build.mjs`, `--full`) | Full `create-eth@2.0.23 se-app -s hardhat` **with** its own `yarn install` (non-interactive). Hardhat: recipe 4c networks inserted into `hardhat.config.ts`, recipe 2 script written to `deploy/`, `yarn compile`, `yarn chain` in the background + `yarn deploy` (must regenerate `deployedContracts.ts` with YourContract on 31337; the node is stopped afterwards), `yarn hardhat:check-types` (only the known rocketh TS2344 errors of errors.md 9 are allowed; anything in `hardhat.config.ts` or `deploy/` fails), and `app/verifySponsorReads.ts` via `hardhat run`, which connects to every recipe 4c network and checks the chain ID. Frontend: variants A and B as above, each with `yarn next:build` (eslint + next build) and `yarn next:check-types`, using the freshly generated `deployedContracts.ts`. |

`fixtures/deployedContracts.ts` is the file `yarn deploy` generated for YourContract in the original test; `typecheck` uses it so the YourContract hooks have types without installing Hardhat and deploying. `build` regenerates it for real.

The repo's default `tsconfig.json` shape (`include: blocks/**/*`) does not fit here: the blocks import `~~/hooks/scaffold-eth`, `~~/utils/...` and `../rocketh/deploy.js` from the generated project, and three of them are fragments (a `targetNetworks` snippet, Hardhat `networks` entries, hook calls without a component). `lib.mjs` sorts the blocks by content, wraps the fragments (`wrapFragment`, `hardhatNetworksFile`) and places each one where the skill says it goes; a block it cannot place fails `typecheck` with a message, so a new block is never silently skipped.

**Not checked:** the Foundry flavour (needs a global Foundry install); `yarn chain` / browser rendering / the burner-wallet write click (the original log did these once by hand); `yarn generate` / `yarn account` (interactive password prompt) and any testnet deploy or contract verification (needs a funded key); `yarn vercel`, `yarn ipfs`, `yarn fork`; extensions (`-e`); the shell blocks in the skill (they are commands, covered by `build` where they matter: `create-eth -s hardhat`, `yarn compile`, `yarn deploy`, `yarn next:build`, `yarn next:check-types`).

Runtimes on a MacBook (Node 24): install 30 to 130 s (the frontend's packages + hardhat; cold npm cache is the slow case), typecheck 7 to 25 s, live 12 to 20 s, build 100 to 220 s (of which create-eth's own `yarn install` is 60 to 90 s with a warm Yarn cache; expect a few minutes more on a cold CI runner). If port 8545 is already taken (another local node), `build` runs the node on a free port and points the template's `default` network at it, so it never deploys to someone else's chain.

No `verify:skip` lines.
